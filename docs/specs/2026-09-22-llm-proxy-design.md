# llm-proxy — дизайн

Дата: 2026-09-22
Статус: согласован, готов к написанию плана реализации

---

## 1. Что строим

Самостоятельный шлюз к LLM-провайдерам поверх [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI),
встроенного **библиотекой**, а не запущенного рядом сервисом. Шлюз добавляет то, чего у
апстрима нет:

1. **Управление ключами** — пользователь сам выпускает и отзывает API-токены в личном кабинете.
2. **Вход через OIDC** — опционально; локальные учётные записи работают всегда.
3. **Ограничение доступа к моделям и провайдерам** — на пользователя, с немедленным эффектом.
4. **Метрики** — потребление, латентность, ошибки, квоты подписок; в Prometheus и в личном кабинете.

Сервис закрытый: самостоятельной регистрации нет.

### Границы MVP

Входит: аутентификация (локальная и OIDC), выпуск/отзыв токенов, политика доступа к моделям,
админка (пользователи, провайдеры, настройки), метрики, журнал активности.

**Не входит:** ограничение потребления токенов (квоты вида «200k за 5 часов»). Форма журнала
потребления закладывается так, чтобы квоты добавились поверх него без миграции данных, но
гейта в MVP нет.

## 2. Опора на апстрим: проверенные факты

Проверено на `github.com/router-for-me/CLIProxyAPI/v7 v7.3.12`. Документация в репозитории
апстрима (`docs/sdk-*.md`) **устарела** — она называет модуль `/v6`; в `go.mod` путь `/v7`.
Сверять API следует с исходником, а не с документацией.

| Возможность | Публичный путь | Назначение у нас |
|---|---|---|
| Встраивание прокси | `sdk/cliproxy.NewBuilder()` | ядро процесса |
| Аутентификация запроса | `sdk/access.RegisterProvider`, `Manager.Authenticate` | токен → принципал |
| Свои middleware и маршруты | `sdk/api.WithMiddleware`, `WithRouterConfigurator`, `WithEngineConfigurator` | гейт политики, свой REST |
| Учёт потребления | `Service.RegisterUsagePlugin(Plugin)` (и глобальный `usage.RegisterPlugin`) | журнал и метрики |
| Конфигурация | `sdk/config.Config` (алиасы на полную структуру) | админка настроек |
| OAuth-вход провайдера | `sdk/api.NewHandlerWithoutConfigFilePath`: `RequestAnthropicToken`, `RequestCodexToken`, `SetPostAuthHook`; `sdk/api.WriteOAuthCallbackFileForPendingSession`, `CompleteOAuthSession` | добавление аккаунта вендора (раздел 9) |
| Управление аккаунтами | `coreauth.Manager`: `List`, `GetByID`, `Register`, `Update`, `Remove` | админка провайдеров |
| Каталог моделей | `cliproxy.GlobalModelRegistry()`: `GetModelProviders` (через утверждение типа — в интерфейсе SDK его нет), `GetAvailableModels` | гейт политики, фильтрация `/v1/models`, каталог админки |
| Подача конфигурации | `WithConfig(*config.Config)`, `WithWatcherFactory` | конфиг структурой, без файла |

### Следствия, определяющие конструкцию

**`sdk/access` отвечает только на вопрос «кто».** `Result{Provider, Principal, Metadata}` не
содержит ни модели, ни маршрута, и точки отказа после выбора модели у него нет. Поэтому
политика доступа — **наш middleware**, а access-провайдер занят исключительно сопоставлением
токена с пользователем.

**Порядок middleware.** `WithMiddleware` регистрируется через `engine.Use()` сразу после
логгера и трассировки (`internal/api/server.go:140-142`), а `AuthMiddleware` вешается на группы
маршрутов позже (`server.go:226`). Значит наш гейт видит запрос **раньше** штатной
аутентификации, и `c.Get("userApiKey")` на этот момент пуст. Гейт обязан разбирать
учётные данные сам — из того же набора источников, что и встроенный провайдер:
`Authorization: Bearer`, `X-Api-Key`, `X-Goog-Api-Key`, `?key=`, `?auth_token=`.

**Управляющая поверхность апстрима не включается.** Маршруты `/v0/management` регистрируются
только когда непусто одно из: `RemoteManagement.SecretKey`, переменная окружения с секретом,
локальный пароль (`server.go:235-239`). Все три остаются пустыми — маршрутов не существует.
Функциональность, которую они предоставляли, берётся напрямую из `sdk/` (таблица выше). Для
входа вендора используются методы обработчика управляющего API из `sdk/api`, но они вызываются
как обычные функции в процессе, а не как маршруты (раздел 9).

**Встроенная статистика мертва.** `UsageStatisticsEnabled` по умолчанию `false`, а
`/v0/management/usage-queue` читается разрушающе (`PopOldest`) и требует единственного
потребителя. Вместо неё — внутрипроцессный sink `usage.RegisterPlugin`; `internal/redisqueue`
регистрируется в апстриме ровно так же.

**Конфигурация подаётся структурой, а не файлом.** `WithConfig` принимает готовый
`*config.Config`, который мы собираем из Postgres. Обновление на лету — через
`WithWatcherFactory`: фабрика получает колбэк `reload func(*config.Config)`, **захватывает его
и возвращает `(nil, nil)`**; все обращения к `s.watcher` в апстриме защищены проверкой на nil
(`builder.go:324`, `service_auth.go:81`, `service_config.go:244`, `service_lifecycle.go:292,341`,
`service_plugins.go:72`). Правка настройки в админке собирает новый `Config` и вызывает
сохранённый `reload` — применение происходит тем же путём, что и при чтении файла.
Следствия: файла конфигурации в рабочем цикле нет вовсе, вопрос «кто пишет файл» не возникает,
а наблюдение за каталогом грантов пропадает — и не требуется, потому что аккаунтами управляет
`coreauth.Manager`. Формальность: `Build()` отвергает пустой `WithConfigPath`
(`builder.go:203`), поэтому путь передаётся, но не читается.

**Обновление каталога моделей запускаем сами.** Бинарник апстрима держит каталог моделей
актуальным тремя фоновыми обновлятелями (`internal/registry`: `StartModelsUpdater`,
`StartCodexClientModelsUpdater`, `StartDevinModelsUpdater`) — они сразу и затем раз в три часа
загружают опубликованный каталог с `raw.githubusercontent.com/router-for-me/models`, а сервис SDK
перерегистрирует модели аккаунтов изменившихся провайдеров (`registerModelRefreshCallback`). Но
запускает их только `cmd/server/main.go` (`startModelCatalogUpdaters`), не сервис SDK: без них
встраивающий процесс знает лишь каталог, вшитый в сборку. Пакет внутренний, обёртки в `sdk/` нет,
поэтому шлюз берёт все три через `//go:linkname` (`internal/infra/gateway/catalog_updaters.go`;
сигнатуры компоновщик не проверяет — при обновлении апстрима их сверяют с исходником) и
запускает после старта сервиса, на его контексте, как апстрим без локального файла моделей и
вне режима Home. Каждый запускается не больше раза за процесс (`sync.Once`).
`LLMPROXY_MODEL_CATALOG_UPDATES=off` их отключает — для тестов и установок без выхода в интернет;
по умолчанию `on`.

**Три места, где взаимодействие не является прямым вызовом.** Всё остальное — обычные вызовы
в одном процессе, без сериализации, сокетов и IPC.

1. **Учёт потребления асинхронен.** `HandleUsage` вызывается фоновой горутиной из
   буферизованной очереди в памяти. Отсюда требование: обработчик обязан быть быстрым и
   не блокирующимся — запись в базу идёт батчами и с таймаутом, иначе очередь растёт.
2. **OAuth-вход вендора — ожидание файла колбэка.** Запуск входа (`RequestAnthropicToken`,
   `RequestCodexToken`) оставляет в апстриме горутину, которая до 5 минут раз в 500 мс ищет в
   каталоге грантов файл колбэка этого входа. Код доставляется записью такого файла, а готовые
   учётные данные возвращаются через post-auth hook. Слушателя порта нет. Решение — в разделе 9.
3. **Исходящие вызовы к провайдерам** — обычная сеть, этим занимается апстрим.

## 3. Архитектура

Один процесс, три поверхности — **на трёх разных слушателях** (уточнено при реализации):

```
  клиенты (Claude Code, omp, чат-панели)        браузер
            │ sk-…                                 │ cookie
            ▼                                      ▼
  ┌─────────────────────────────────────────────────────────┐
  │  policy middleware        │  REST /api/*   │  /metrics   │
  │  ─────────────────        │  ───────────   │             │
  │  резолв токена            │  ЛК, админка   │  Prometheus │
  │  предикат политики        │                │             │
  │  фильтр /v1/models        │                │             │
  └───────────┬───────────────┴────────┬───────┴─────────────┘
              ▼                        ▼
      встроенный cliproxy          application layer
              │                        │
              ▼                        ▼
       OAuth-гранты вендоров       PostgreSQL
              │                        ▲
              └── usage sink ──────────┘
```

Фронтенд — отдельная сборка (React), отдаётся статикой; в разработке через Vite dev-server с
проксированием `/api`.

**Почему три слушателя, а не один.** Если веб-API и прокси делят один порт, то
`/api/admin/...` отвечает и на публичном имени API, которое раздаётся всем клиентам. Поэтому:

| Слушатель | Что на нём | Кто достаёт |
|---|---|---|
| прокси (`LLMPROXY_LISTEN_ADDR`) | проксируемый LLM API; гейт политики — default-deny | обратный прокси, публично |
| веб-API (`LLMPROXY_WEB_ADDR`) | `/api/*` кабинета и админки, сессии | только контейнер фронтенда: общая с ним сеть compose |
| метрики (`LLMPROXY_METRICS_ADDR`) | `/metrics` | только сборщик, подключённый к сети метрик compose |

Админка тем самым физически недоступна с адреса, который выдаётся клиентам, а гейт прокси не
обязан знать про веб-маршруты.

### Слои (DDD)

```
domain/          сущности, value objects, инварианты; без зависимостей от инфраструктуры
application/     сценарии использования, транзакционные границы, порты
infrastructure/  postgres, oidc, cliproxy, prometheus — реализации портов
interfaces/      http-обработчики, middleware, dto
```

Правило: `domain` не импортирует ничего из проекта, `application` знает только `domain` и
собственные порты, `infrastructure` и `interfaces` зависят внутрь. Обратных зависимостей нет.

### Ограниченные контексты

| Контекст | Агрегаты и объекты | Отвечает за |
|---|---|---|
| `identity` | `User` (агрегат), `Password`, `FederatedIdentity`, `Session` | кто человек, как он входит, роль |
| `access` | `Policy` (VO), `ModelRule` (VO), `Catalog` | что человеку можно |
| `credentials` | `ApiToken` (агрегат) | чем он предъявляет себя API |
| `usage` | `UsageEvent`, `UsageQuery` | сколько израсходовано |
| `audit` | `AuditEvent` | что происходило |
| `providers` | `VendorAccount`, `ProxySettings` | аккаунты вендоров и настройки апстрима |

## 4. Модель доступа

### 4.1 Правило — предикат, а не список

`Policy` — множество правил вида `<provider>:<model-glob>`:

```
chatgpt:*                  весь провайдер, включая модели, которых ещё нет
claude:claude-sonnet-5     ровно одна модель
*:*                        всё
```

**Правило вычисляется на каждом запросе против живого каталога, а не разворачивается в
перечень при выдаче.** Это ключевое свойство: новая модель у провайдера становится доступна
обладателю `chatgpt:*` автоматически, без правки прав.

**Диалект шаблона — ровно два символа: `*` и `?`.** `*` покрывает любую последовательность,
включая `/` и `:`, `?` — ровно один символ; всё остальное сравнивается буквально, поэтому
`claude.sonnet` не совпадёт с `claudexsonnet`, а `[a-z]` это текст, а не класс символов.
Шаблон якорится с обоих концов.

Это не мелочь оформления, а следствие того, что **идентификаторы моделей — не пути**.
Файловый глоб не переходит через `/`, и правило `openrouter:*claude*` молча не совпало бы с
`anthropic/claude-sonnet-4.6`: отказ закрытый и невидимый — ровно тот случай, ради которого
вся конструкция и затевалась. По той же причине правило режется по **первому** двоеточию:
`ollama:llama3:70b` и `bedrock:…-v1:0` — настоящие идентификаторы, и при делении по каждому
двоеточию выразить их было бы нечем, кроме `provider:*`.

Deny-правил нет намеренно. Allow-множество замкнуто относительно объединения, порядок правил
не имеет значения, и на вопрос «почему не пускает» всегда отвечает отсутствие покрывающего
правила. Deny ломает все три свойства.

Проверка идёт по **запрошенной** модели, включая алиас: `Record.Alias` и `usage.WithRequestedModelAlias`
показывают, что апстрим различает запрошенное и исполненное имя. Политика применяется к
запрошенному — иначе алиас становится обходным путём.

### 4.2 `/v1/models` фильтруется тем же предикатом

Без этого ограничение косметическое: клиент строит список моделей из ответа `/v1/models`,
пользователь выбирает недоступную и получает отказ на отправке. Фильтрует сам гейт политики:
таблица маршрутов помечает `GET /v1/models`, `GET /v1beta/models` и `GET /v1beta/models/*`
как маршруты-перечни, гейт придерживает ответ апстрима (обёрткой `ResponseWriter` — после
`c.Next()` тело было бы уже отправлено) и оставляет только модели, которые пропустил бы
запрос к ним. Список неожиданной формы или больше 16 МиБ не отдаётся (502).

### 4.3 Права принадлежат пользователю, не токену

Токен прав не несёт: это именованный отзываемый ключ устройства, привязанный к владельцу.
Следствие — правка политики действует **немедленно**, со следующего запроса, и не требует
перевыпуска токенов.

Кэша политики нет: владелец токена читается из базы на каждом запросе, одним чтением вместе с
резолвом токена, и его политика приходит с этим чтением. Поэтому правка действует со следующего
запроса без какой-либо инвалидации.

### 4.4 Источник политики

По образцу Grafana (`skip_org_role_sync` / `auto_assign_org_role`):

| Конфигурация развёртывания | Источник политики | Правится в админке |
|---|---|---|
| OIDC выключен | админка | да |
| OIDC включён, маппинг групп не задан | админка, новым выдаётся `default_policy` | да |
| OIDC включён, маппинг групп задан | claims, пересчёт при каждом входе | нет, отметка «managed by IdP» |

**`policy_managed_by` — поле пользователя, а не только настройка развёртывания.** В смешанном
развёртывании локальному пользователю claims взять неоткуда, поэтому его политику правит админ
даже при включённом маппинге. Глобальная настройка задаёт умолчание и включён ли sync вообще;
строка пользователя помнит владельца прав. Без этого включение маппинга молча обнулило бы
локальные учётные записи в `default_policy`.

Синхронизация происходит на входе — как в Grafana. Фонового опроса IdP нет: политика
материализована на пользователе, и для запроса с `sk-…` claims не нужны.

## 5. Идентичность и провижининг

### 5.1 Сосуществование локальных и федеративных учётных записей

Человек и способ входа разведены:

```
users              id, kind, email, display_name, role, policy, policy_managed_by, status
user_passwords     user_id, hash                          ← локальный вход
user_identities    user_id, issuer, subject               ← OIDC, UNIQUE(issuer, subject)
```

Один пользователь может иметь оба способа: токены и политика у него одни, потому что `user_id`
один. Привязка второго способа делается явно, залогиненным пользователем.

**Сопоставление по `subject`, не по почте.** Почта меняется, `sub` стабилен. Автоматическая
привязка OIDC-входа к существующей локальной учётной записи по совпадению email — известный
вектор захвата учётной записи (Grafana закрыла его флагом `oauth_allow_insecure_email_lookup`,
выключенным по умолчанию). У нас автопривязки по почте нет; есть опция для доверенного IdP,
выключенная по умолчанию.

### 5.2 Регистрации нет

**Эндпоинта самостоятельной регистрации не существует** — не «выключен флагом», а отсутствует.
Учётные записи заводит только администратор.

Выдача локальной учётной записи:

1. Админ создаёт пользователя, система генерирует временный пароль.
2. Пароль **показывается один раз**, хранится сразу как argon2id-хэш, в логи и ответы API
   не попадает.
3. Временный пароль, выданный администратором, живёт 72 часа. Это константа
   (`app.TemporaryPasswordTTL`), а не настройка. Протух — админ перевыпускает.
4. У пользователя стоит `must_change_password`. Сессия, полученная по временному паролю,
   **урезана**: пропускает только смену пароля, остальное отдаёт 403. Иначе флаг вырождается
   в баннер, который игнорируют.

Бутстрап-администратор (`LLMPROXY_BOOTSTRAP_ADMIN_EMAIL`) создаётся при первом старте со
случайным паролем и тем же `must_change_password`. Пароль печатается один раз в поток ошибок
процесса, минуя логгер. Срока жизни у него нет: существующий администратор подавляет любой
следующий бутстрап, и оператор, не успевший в срок, остался бы без входа.

### 5.3 Закрытость при включённом OIDC

Локальная регистрация убрана, но OIDC-вход по умолчанию заводит пользователя сам — и тогда
войти может любой член realm. Два гейта, включаются оба:

| Гейт | Действие |
|---|---|
| Обязательная группа | пускаем только члена заданной группы (имя группы — настройка) |
| `allow_sign_up = false` | вход только для существующего пользователя; неизвестный `sub` отбивается |

При `allow_sign_up = false` админ заводит человека заранее и помечает ожидаемый email для
входа через IdP. Первый вход по этому email привязывает `sub`, пометка гасится. Это не та
автопривязка по почте, о которой предупреждает 5.1: там связывание молчаливое и автоматическое,
здесь — однократное и по явному решению администратора.

### 5.4 Защита от самоблокировки

- Первый запуск создаёт локального администратора, если задан `LLMPROXY_BOOTSTRAP_ADMIN_EMAIL`.
- `LLMPROXY_LOCAL_LOGIN=false` выключает локальный вход в OIDC-развёртывании. Тогда
  `GET /api/auth/config` отдаёт `localLogin: false`, форма не показывается, а
  `POST /api/auth/login` отвечает 404, как отсутствующий маршрут. По умолчанию `true`.
  Аварийное включение — вернуть `true` и перезапустить процесс: падение IdP не должно означать,
  что в админку не войти никому. Бутстрап-администратор создаётся и при `false` (с
  предупреждением в логе), но войти им можно только после включения.
- Троттлинг: 5 неудачных попыток входа по одному адресу учётной записи блокируют вход по этому
  адресу на 15 минут (о цене — раздел 17).

### 5.5 Сервисные учётные записи

Машинным потребителям (чат-панель, интеграция, скрипт) нужен токен, но человеком они не
являются. Выдавать им ключ с личной учётной записи администратора нельзя: расход смешается
с личным, политика администратора обычно шире всех, а блокировка человека убьёт работающую
интеграцию.

Поэтому у `users` есть поле `kind`: `human` или `service`. **Это флаг, а не параллельная
иерархия** — сервисная учётная запись остаётся пользователем, поэтому политика, журнал
потребления, метрики и `last_seen_at` работают для неё тем же кодом. Требование «ограничения
привязаны к пользователю» не нарушается.

Отличия ровно три:

- нет пароля и нет привязки OIDC — записей в `user_passwords` и `user_identities` не бывает;
- **войти в веб-интерфейс нельзя** — сессия для `kind = service` не создаётся ни при каких
  условиях;
- токены выпускает и отзывает администратор, а не сам аккаунт.

`policy_managed_by` у сервисной записи всегда локальный: claims ей взять неоткуда, и включение
маппинга групп её не касается.

Побочный эффект, важный для метрик: каждый машинный потребитель получает **собственную строку
в разрезах по пользователю** вместо растворения в чьём-то личном расходе. Расход по людям
*внутри* такой панели этим не возвращается — это телеметрия самой панели.

## 6. Токены

- Формат `sk-` + случайная часть достаточной энтропии. Показывается один раз при выпуске.
- В базе — `sha256` и префикс для отображения (`sk-…a1b2`). Восстановить значение нельзя.
- Поля: владелец, ярлык, создан, `last_used_at`, состояние (активен / отозван), кем отозван.
  Владелец — любая учётная запись, включая сервисную; у сервисной выпуск и отзыв доступны
  только администратору.
- Отзыв немедленный: токен и его владелец читаются на каждом запросе, кэша нет.
- У одного владельца не больше 50 живых (неотозванных) токенов (`app.MaxLiveTokensPerOwner`);
  выпуск сверх этого — 409 `token_limit`.
- Резолв токена делает наш access-провайдер, регистрируемый через `sdk/access`; `Principal`
  несёт идентификатор пользователя, что связывает записи `usage.Record.APIKey` с владельцем.

## 7. Журналы

Два журнала с разным назначением и разным сроком жизни. Смешивать нельзя — иначе ретеншн
становится неописуемым.

| | `usage_events` | `audit_events` |
|---|---|---|
| Пишет | usage-sink, асинхронно | application-слой, синхронно |
| Содержит | провайдер, модель, алиас, токены по видам, латентность, TTFT, стрим, тир, статус, аккаунт вендора | вход, выпуск и отзыв токена, правка политики, создание пользователя, смена пароля, правка настроек |
| Ретеншн | по политике, допускает прореживание | не удаляется |
| Потребители | ЛК, `/metrics`, будущие квоты | админка, разбор инцидентов |

**Последняя активность.** В админке — объединение обоих журналов. Чтобы список пользователей
не считал агрегат на строку, денормализованы `users.last_seen_at` и `api_tokens.last_used_at`;
обновляет их тот же асинхронный sink, а не горячий путь запроса.

В личном кабинете список ключей показывает ярлык, префикс, дату создания, **последнее
использование** и состояние.

## 8. Метрики

Источник — `usage.Plugin.HandleUsage(ctx, Record)`, внутрипроцессный, с буферизованной очередью.
`Record` несёт: `Provider`, `Model`, `Alias`, `APIKey`, `AuthID`, `AuthType`, `Stream`,
`ServiceTier`, `ReasoningEffort`, `Latency`, `TTFT`, `Failed`, `Fail.StatusCode`, `Detail`
(включая канонический `TokenBreakdown` с полем качества учёта) и **`ResponseHeaders`**.

Три следствия:

- **Квоты подписок приходят сами.** Заголовки вендора (`Anthropic-Ratelimit-Unified-5h-Utilization`,
  `X-Codex-Primary-Used-Percent` и парные `Reset`) лежат в `ResponseHeaders` каждого ответа.
  Опрос по таймеру не нужен.
- **`TokenBreakdown` каноничен**, с явным признаком качества. Ручная разбивка на
  input/output/reasoning/cache и борьба с двойным счётом рассуждений не нужны. Снимается и
  опасение про усечение `usage` у OpenAI-стриминга без `stream_options.include_usage`.
- **Состояние не персистится.** Журнал лежит в Postgres, счётчики Prometheus стартуют с нуля,
  сброс обрабатывает `rate()`.

### Ревизия семейств

Пересмотр существующего экспортера. Префикс всех семейств — `llmproxy_`.

| Было | Решение |
|---|---|
| `cpa_up` | убрать: дублирует штатный `up` скрейпа; вместо него `build_info{version}` |
| `quota_used_ratio`, `quota_reset_timestamp_seconds`, `quota_observed_timestamp_seconds` | переименованы в `vendor_quota_used_ratio`, `vendor_quota_reset_timestamp_seconds`, `vendor_quota_observed_timestamp_seconds`, метки `{account,provider,window}`; источник — `ResponseHeaders` |
| `account_disabled`, `account_failures_total` | оставить, метки `{account,provider}`; теперь точные (`Auth.Disabled`, `Failed`) |
| `tokens_total`, `requests_total` | оставить; метка-ярлык ключа заменяется меткой `user`: `tokens_total{user,provider,model,service_tier,kind}`, `requests_total{user,provider,model,stream,status}`. Метки `token` нет ни в одном семействе |
| `cost_usd_total`, `cost_unpriced_tokens_total` | оставить (`{user,provider,model}` и `{provider,model}`); прайс — таблица в базе под админкой, а не загрузка чужого файла с внешнего репозитория |
| `prices_loaded_timestamp_seconds`, `prices_models` | **не реализованы в бете**: таблица цен не хранит ни момента загрузки, ни числа моделей. Пустой прайс виден по росту `cost_unpriced_tokens_total` |
| `request_latency_ms_sum/count`, `ttft_ms_sum/count` | переделаны в гистограммы в секундах: `request_duration_seconds{provider,model,stream}`, `ttft_seconds{provider,model}`; значения поштучные, квантили настоящие |
| `librechat_*` | не наше: телеметрия внешней панели, собирается из её собственной базы |

Добавляются: `policy_denied_total{user,model,reason}` (`reason`: `model_not_allowed`,
`unknown_model`, `route_not_allowed`; модель, которой нет в каталоге, пишется как `unknown`) и
`auth_failures_total{reason}` (`missing`, `invalid`).

**Кардинальность.** `user × model × kind` — при десятках пользователей приемлемо. Метки `token`
в метриках нет: число ключей не ограничено сверху так, как число пользователей, а на вопрос
«каким ключом пользовались» отвечает журнал `usage_events` (`token_id`).

**Графики в личном кабинете считаются из Postgres**, а не из Prometheus: кабинету нужны точные
числа и своя глубина, а не окно ретеншна системы мониторинга. Один журнал, два потребителя.

## 9. Управление провайдерами и настройками

Админка работает напрямую через SDK, управляющая поверхность апстрима не поднимается.

**Аккаунты вендоров:** список из `coreauth.Manager.List()` с состоянием (`Status`, `Disabled`,
`LastError`, `LastRefreshedAt`) и последними сигналами квоты по окнам, которые usage-sink
снимает с заголовков ответов вендора; отключение и удаление — `Update` и `Remove` через шлюз.
Принудительного обновления гранта (`ForceRefreshAuth`) и сброса квоты (`ResetQuota`) в бете
нет: маршрутов для них не заведено.

**Добавление аккаунта — путь встраивающего приложения из `sdk/api`.** Штатный `sdk/auth`
`Login` рассчитан на терминал и поднимает локальный слушатель для колбэка, что для веб-админки
непригодно. Поэтому шлюз создаёт обработчик управляющего API
(`NewHandlerWithoutConfigFilePath`) и вызывает его методы напрямую, не публикуя маршрутов:

1. `start` вызывает `RequestAnthropicToken` (Claude) или `RequestCodexToken` (ChatGPT) на
   синтетическом gin-контексте без `is_webui` и читает из ответа `{url, state}`. Без `is_webui`
   апстрим слушателя колбэка не поднимает; он оставляет горутину, ждущую файл колбэка этого
   входа в каталоге грантов. Админка показывает ссылку, человек проходит вход в своём браузере.
2. `complete` принимает вставленный callback-URL. URL без кода или со `state` чужого входа
   отклоняется, а вход остаётся ожидающим — можно вставить ещё раз. Иначе вход захватывается
   ровно один раз, и код передаётся апстриму через `WriteOAuthCallbackFileForPendingSession`
   (файл 0600, апстрим читает и удаляет его).
3. Апстрим обменивает код и отдаёт готовую запись в post-auth hook (`SetPostAuthHook`) до
   собственного сохранения. Хук передаёт её ожидающему `complete` и возвращает ошибку, так что
   апстрим не сохраняет ничего сам; аккаунт добавляет шлюз через `AddAccount`.
4. Аккаунт, который не удалось сохранить или записать в аудит, снимается обратно: учётные
   данные не входят в работу без записи.

Ограничения: вход действителен 5 минут с момента `start` (столько ждёт апстрим); одновременно
ожидают не больше 8 входов, девятый — 409 `login_busy`; `complete` ждёт обмена кодом не дольше
минуты; просроченный, завершённый или уже захваченный вход — `login_expired`. Любой исход
завершает сессию апстрима (`CompleteOAuthSession`), и его горутина останавливается.
Проброс порта туннелем не нужен: порт не открывается вовсе.

Принятые остатки: брошенное после `complete` завершение может оставить код в файле 0600 в
каталоге грантов; `proxy-url`, применённый на лету, попадает в обмен кодом только после
перезапуска; апстрим пишет в лог ошибку сохранения при каждом успешном входе — её вызывает хук,
останавливающий его собственное сохранение.

**Сверка после каждой правки аккаунтов — обязательна, и это проверено экспериментом.**
Watcher у нас пустой, а именно его очередь обновлений у апстрима регистрирует модели
аккаунта в глобальном реестре. Поэтому поведение такое (замер на v7.3.12, грант Claude):

| Действие | Без повторного применения конфига | С повторным применением |
|---|---|---|
| грант лежит в каталоге при старте | 16 моделей | — |
| `Register` после старта | аккаунт в менеджере, **0 моделей** — не маршрутизируется | 16 |
| `Update(Disabled)` | модели **остаются** | 0 |
| `Remove` | модели **остаются** | модели **остаются** |

Отсюда протокол, который держит шлюз, а не вызывающий: добавление — `Register`, затем
повторное применение текущего конфига; отключение — `Update`, затем применение; удаление —
**сначала** отключение с применением, **потом** `Remove`. Прямой `Remove` оставляет модели
висеть в `/v1/models`: учётки уже нет, запрос упадёт на исполнении, но клиент видит модель,
которой нельзя воспользоваться. Поскольку поведение принадлежит апстриму и может смениться
при обновлении, оно закрепляется тестами, а не только текстом.

**Учётные данные из конфига в рантайме не добавляются.** Колбэк, который мы захватываем, —
`applyWatcherConfigUpdate`, он вызывает применение конфига с отключённым синтезом
учётных данных (настоящий watcher шлёт их отдельно), а вариант с синтезом не вызывается
в апстриме нигде. Семейства `*-api-key` и `openai-compatibility` поэтому задаются только
в конфиге при старте; их правка требует перезапуска. OAuth-аккаунты вендоров, ради которых
шлюз существует, живут в менеджере и этим ограничением не затронуты.

**Настройки апстрима:** источник правды — Postgres. Изменение собирает новый
`*config.Config` и применяется вызовом захваченного `reload` (раздел 2); файла конфигурации
в рабочем цикле нет. В MVP формами покрываются: аккаунты, `proxy-url`, параметры ретраев,
стратегия роутинга, алиасы и исключения моделей, настройки логирования. Аварийный люк —
редактор сырого YAML, который разбирается в типизированный `sdk/config.Config` и проходит ту
же валидацию, что и формы. Остальные поля переезжают в формы по мере надобности, без
изменения конструкции.

## 10. Хранилище

PostgreSQL, драйвер `pgx/v5` (уже присутствует в зависимостях апстрима — второй драйвер не
вводится), миграции `goose`.

```
users              id, kind, email, display_name, role, status, policy, policy_managed_by,
                   must_change_password, last_seen_at, created_at
user_passwords     user_id, hash, updated_at
user_identities    user_id, issuer, subject, linked_at        UNIQUE(issuer, subject)
pending_identities user_id, issuer, expected_email, expires_at ← для allow_sign_up=false

                   ← «урезанность» сессии НЕ хранится: она выводится при чтении из

                     сессия, открытая до выдачи временного пароля, осталась бы полной
api_tokens         id, user_id, label, hash, prefix, created_at, last_used_at,
                   revoked_at, revoked_by

                   tokens_cache_write, tokens_total, breakdown_quality,
```

## 11. Фронтенд

React + TypeScript, сборка Vite. Компоненты свои, на CSS Modules; UI-кит не подключается —
он тянет собственную систему оформления, которую пришлось бы переопределять под наши токены,
и это гарантированный дрейф дизайна.

**Токены оформления** совпадают с существующей страницей-инструкцией:
`--bg`, `--panel`, `--line`, `--fg`, `--dim`, `--accent`, `--code`.
Четыре темы (`auto`, `light`, `pink`, `dark`), два языка (`en`, `ru`), выбор в `localStorage`,
применение **до первой отрисовки** — иначе при каждой загрузке мигает умолчание.
Умолчания при пустом хранилище: язык `en`, тема `auto` (следует `prefers-color-scheme`).

Отличие от статической страницы осознанное: там оба языка лежат в разметке и переключаются
правилом CSS, здесь — обычные словари. Для одностраничной инструкции дублирование разметки
дёшево, для приложения с формами и таблицами — нет.

**Экраны:**

| Путь | Содержание |
|---|---|
| `/login` | форма входа и/или кнопка OIDC, в зависимости от конфигурации |
| `/password` | смена временного пароля; единственное, что доступно урезанной сессии |
| `/` | кабинет: ключи (ярлык, префикс, создан, последнее использование, отзыв), свой расход |
| `/connect` | инструкция подключения с **подставленным** токеном и адресами из конфигурации |
| `/admin/users` | пользователи: последняя активность, роль, политика, выдача и блокировка |
| `/admin/providers` | аккаунты вендоров: состояние, квота, добавление по OAuth, отключение |
| `/admin/settings` | настройки апстрима, прайс-лист, аварийный редактор YAML |

Экран `/connect` заменяет отдельную статическую страницу-инструкцию: адреса и готовые блоки
для клиентов собираются из конфигурации, а не пишутся в разметке, поэтому в коде нет ни одного
имени конкретного развёртывания.

## 12. Конфигурация и нейтральность кода

Репозиторий предназначен к публикации. Поэтому:

- **Ни одного имени хоста, домена, realm, группы, IP или пути конкретного развёртывания** —
  ни в коде, ни в примерах. Примеры используют `example.com` и обобщённые имена.
- Всё задаётся переменными окружения и конфигурационным файлом; в репозитории лежат только
  `*.example` с нейтральными значениями.
- Секреты не логируются и не возвращаются API — включая временные пароли и значения токенов
  (кроме единственного показа при выпуске).
- Перед публикацией история коммитов проверяется отдельно: приватность репозитория в период
  разработки сама по себе от утечки в истории не защищает.
- Ветка `sdd-ledger` удаляется — локально и на origin — **до** открытия репозитория. В ней
  журнал разработки и отчёты ревью с локальными путями; она существует как резервная копия
  git-игнорируемого рабочего каталога и публикации не подлежит.

Основные настройки (переменные окружения): адреса трёх слушателей (`LLMPROXY_LISTEN_ADDR`,
`LLMPROXY_WEB_ADDR`, `LLMPROXY_METRICS_ADDR`), строка подключения к базе
(`LLMPROXY_DATABASE_URL`), параметры OIDC (`LLMPROXY_OIDC_*`: issuer, client, redirect,
требуемая группа, claim групп, маппинг групп в политику, политика по умолчанию, `allow_sign_up`,
подпись кнопки входа), `LLMPROXY_LOCAL_LOGIN` (раздел 5.4), `LLMPROXY_MODEL_CATALOG_UPDATES`
(обновление каталога моделей из сети, раздел 2), почта бутстрап-администратора,
ключ сессий и флаг `Secure` для cookie, публичный адрес API для `/connect`, пути каталога
грантов (`LLMPROXY_AUTH_DIR`) и рабочего каталога (`LLMPROXY_RUNTIME_DIR`). Срок жизни
временных паролей — не настройка, а константа (раздел 5.2).

## 13. Развёртывание

Один `docker-compose.yml`, три сервиса.

| Сервис | Образ | Роль |
|---|---|---|
| `postgres` | официальный, тег пинуется | хранилище |
| `backend` | сборка из этого репозитория | прокси, REST, `/metrics` |
| `frontend` | nginx со статикой | веб-интерфейс, проксирует `/api` на `backend` |

**Тома — три, и один из них критичен.**

| Том | Что в нём | Последствие потери |
|---|---|---|
| данные базы | пользователи, токены, журналы | потеря всего состояния |
| **каталог грантов** | **OAuth-гранты вендоров** | **все аккаунты заводятся заново** |
| рабочий каталог | логи запросов апстрима | потеря логов |

Каталог грантов обязан быть именованным томом. Без него пересоздание контейнера — обычная
операция при обновлении — стирает входы во все аккаунты вендоров.

**Путь конфигурации задаётся, но файла там нет.** `Build()` отвергает пустой `WithConfigPath`
(`builder.go:203`), и тот же путь уходит в `api.NewServer` для разрешения каталога логов
(`service_lifecycle.go:126`). Поэтому путь указывает в рабочий том; конфигурация при этом
приходит структурой из Postgres (раздел 2), и файл по этому пути не создаётся и не читается.

**Миграции применяются бэкендом при старте**, до приёма запросов. При неуспехе миграции
процесс не поднимается — шлюз с неизвестной схемой хуже, чем отсутствующий.

**Проверки готовности:** у базы — штатная проба, у бэкенда — `/healthz` на проксируемом
слушателе (маршрут апстрима, открытый в таблице маршрутов гейта),
у фронтенда — отдача индексной страницы. Зависимости выражены условием готовности, а не
простым порядком запуска.

**Публикация портов и сети.** Наружу торчит только то, что нужно обратному прокси; база не
публикуется вовсе. TLS и маршрутизация имён — на обратном прокси вне compose: веб-имя ведёт
на `frontend`, имя API — на `backend`. Внутри compose сети разделены: веб-слушатель бэкенда
виден только в сети `web` (бэкенд и фронтенд), база — только в сети `db` (бэкенд и postgres),
метрики — в сети `metrics`, к которой оператор подключает свой сборщик. Ограничение частоты
запросов веб-API доверяет `X-Real-IP` именно потому, что до веб-слушателя достаёт только
nginx фронтенда.

**Сборка при двух репозиториях.** Основной compose **собирает из исходников**: бэкенд из
этого репозитория, фронтенд из соседнего склонированного каталога. Это единственный вариант,
при котором `docker compose up` работает с первого дня — публиковать образы пока нечем и
некуда, конвейера сборки и реестра не существует. Переход на опубликованные образы —
отдельный overlay-файл, появляющийся вместе с конвейером, а не раньше.

**Секреты только из `.env`**, в репозитории — `.env.example` с нейтральными значениями: пароль
базы, параметры провайдера OIDC, учётные данные начального администратора. В `docker-compose.yml`
значений секретов нет.

Образ бэкенда собирается многоступенчато, финальный слой без инструментов сборки, процесс
работает не от root. Теги базовых образов пинуются — обновление остаётся осознанным шагом.

## 14. Обработка ошибок

| Ситуация | Ответ |
|---|---|
| Нет учётных данных | 401, без раскрытия существования токена |
| Токен неизвестен, отозван или владелец заблокирован | 401 |
| Модель не покрыта политикой | 403 с указанием запрошенной модели, без перечисления доступных |
| Урезанная сессия вне смены пароля | 403 |
| Отказ апстрима | пробрасывается как есть, фиксируется в `usage_events` с кодом |
| Недоступна база | 503; запросы к прокси не обслуживаются, потому что решение о доступе принять нельзя |

Последнее — сознательный выбор fail-closed: шлюз, пускающий всех при недоступном хранилище
политик, не является средством ограничения доступа.

## 15. Проверка

Требование к конструкции, а не только к дисциплине: **ни один кусок функциональности не должен
проверяться вручную curl'ом**. Ручная проверка не повторяема, не запускается на каждое
изменение и молча деградирует. Поэтому тестовая обвязка закладывается до кода, а не после.

### Поддельный провайдер — ключ ко всему

`coreauth.Manager.RegisterExecutor(ProviderExecutor)` публичный. Значит в тестах поднимается
**настоящий** встроенный сервис, но вместо вендора зарегистрирован поддельный исполнитель:
отдаёт заготовленные ответы, умеет стриминг, умеет отказывать заданным кодом и публикует
записи потребления через `usage.PublishRecord`.

Следствия: сквозные тесты идут без живых OAuth-грантов, без сети наружу, без расхода квоты
подписки и детерминированно. Отказы вендора (429, 503, обрыв потока) воспроизводятся по
требованию, а не ловятся случайно в проде.

### Уровни

| Уровень | Что проверяет | Чем |
|---|---|---|
| Домен | предикат политики (включая покрытие будущей модели через `*`), переходы состояний токена, правила урезанной сессии | модульные тесты, без инфраструктуры |
| Хранилище и сценарии | выдача и отзыв, смена временного пароля, первый вход по OIDC при `allow_sign_up=false`, привязка `sub` | реальный Postgres в контейнере, поднимается тестом |
| Гейт | отказ по непокрытой модели, фильтрация `/v1/models`, разбор всех источников учётных данных, поведение при недоступной базе | `httptest` на собранном роутере |
| Сквозной | запрос разрешённой и запрещённой модели, появление записи в `usage_events`, значения в `/metrics`, применение правки политики без перевыпуска токена | поднятый сервис с поддельным провайдером |
| Конфигурация | правка настройки применяется вызовом захваченного `reload` | сквозной тест с проверкой поведения после применения |

### Моки — генерируются mockery, не пишутся руками

Все моки интерфейсов производит **mockery**. Рукописных моков в репозитории нет.

Причина не в экономии печати: рукописный мок не ломается, когда интерфейс меняется, — он
продолжает компилироваться со старым набором методов, и тест начинает проверять контракт,
которого больше не существует. Сгенерированный мок при расхождении не соберётся.

Правила:

- Конфигурация `.mockery.yaml` в корне; генерация — одной командой, той же, что в CI.
- Мокируются **порты приложения** (репозитории, клиент OIDC, часы, генератор секретов,
  публикатор записей потребления) — то есть интерфейсы, которые объявляем мы сами.
  Чужие типы не мокируются: для апстрима есть поддельный исполнитель.
- Сгенерированный код **коммитится**, чтобы сборка и тесты не требовали установленного
  инструмента. Расхождение сгенерированного кода с интерфейсами проверяется в CI.
- Ожидания задаются типобезопасным API генератора, а не строковыми именами методов.

Исключение одно и оно осознанное: **поддельный исполнитель провайдера** — это не мок, а
поведенческая подделка с состоянием (последовательности потоковых чанков, задержки,
воспроизводимые отказы). Мок проверяет вызовы, а здесь нужно поведение. Там, где важны ещё и
сами вызовы, подделка строится поверх сгенерированного мока, а не вместо него.

### Требования к обвязке

- **Одна команда** запускает всё; она же выполняется в CI. Разделение на быстрые и медленные
  прогоны допустимо, но «забытых» наборов быть не должно.
- **Реальный Postgres, не подделка.** Половина логики здесь — запросы и ограничения целостности;
  на заглушке они не проверяются.
- **Изоляция:** каждый тест получает чистую схему, порядок выполнения на результат не влияет.
- **Помощники создают состояние через публичные сценарии приложения**, а не вставками в
  таблицы: иначе тесты перестают замечать поломки самих сценариев.
- **Каждый исправленный баг получает тест**, падающий до исправления.
- Проверка утечек: тест, убеждающийся, что значения токенов, паролей и секретов не попадают
  в ответы API и в логи. Это тот класс ошибок, который вручную не ловится вовсе.

### Что остаётся ручным

Только внешний вид: экраны в браузере, все четыре темы, оба языка, ширина телефона — вопрос
вкуса и контраста. Поведение автоматизировано полностью, включая отсутствие вспышки темы при
загрузке: это регрессия порядка подключения скриптов, а не вопрос вкуса (раздел 9 спеки
фронтенда).

## 16. Вне текущего объёма

- Ограничение потребления токенов (окна, тарифы, `Retry-After`). Журнал к этому готов.
- Оценка ёмкости окна квоты («сколько примерно токенов ещё влезет»). Из метрик квоты
  остаются только прямые сигналы вендора: доля израсходованного, момент сброса, время
  последнего наблюдения.
- Преагрегация метрик, если вырастут объёмы.
- Командная работа: организации, общие ключи, делегирование администрирования.
- Автоматическая выдача учётных записей по членству в группе IdP без участия администратора.

## 17. Риски

| Риск | Что делаем |
|---|---|
| Апстрим меняет публичный SDK между версиями | версия модуля пинуется; обновление — осознанный шаг с прогоном тестов гейта |
| Документация апстрима расходится с кодом (уже наблюдается: `/v6` против `/v7`) | опора только на исходник |
| Окно рассинхронизации политики при sync из IdP | синхронизация на входе, как в Grafana; правка в админке действует немедленно |
| Рост кардинальности метрик | метки ограничены; метки `token` нет, детализация по ключу — в журнале |
| Утечка имён развёртывания в публичный репозиторий | нейтральность кода как правило; проверка истории перед публикацией |

### Известные ограничения беты

Приняты сознательно; каждое закрывается окружением, а не кодом.

- **Медленные клиенты на проксируемом слушателе (slowloris).** Его `http.Server` строит
  апстрим, без таймаутов заголовков и простоя, и точки, чтобы их задать, SDK не даёт. Защиту
  несёт обратный прокси перед шлюзом со своими таймаутами; проксируемый слушатель не
  выставляется наружу напрямую — только через обратный прокси или в доверенной локальной сети.
  Веб-слушатель и слушатель метрик строим мы сами, и таймауты у них есть.
- **Целевая блокировка известной локальной учётной записи.** Троттлинг считает неудачные
  попытки по адресу учётной записи, без аутентификации: кто знает адрес, может пятью
  попытками заблокировать локальный вход по нему на 15 минут и повторять это. Блокировка
  действует только в пределах окна и не касается OIDC: вход через IdP — аварийный путь
  («break-glass») для такой учётной записи. В развёртывании без OIDC остаётся ждать окончания
  окна.
