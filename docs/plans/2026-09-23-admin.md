# llm-proxy admin backend — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The administrator's half of the web API — users and service accounts, vendor accounts with a browser-friendly login wizard, settings and prices — plus the composition root that turns every piece of both plans into one running process.

**Architecture:** Application services in `internal/app` behind the ports already declared, HTTP handlers in `internal/iface/http` implementing `api/openapi.yaml`, and a composition root in `internal/boot` (`boot.Run`; `cmd/gateway/main.go` only calls it) wiring three listeners: the proxied LLM API (public, behind the reverse proxy), the web API (reachable only from the frontend container), and metrics (reachable only inside the deployment network).

**Tech Stack:** as the core plan, plus `github.com/oapi-codegen/oapi-codegen/v2` for request and response types generated from the contract (types only; see `internal/iface/http/api/codegen.yaml`).

**Spec:** `docs/specs/2026-09-22-llm-proxy-design.md`. **Contract:** `api/openapi.yaml`. **Depends on:** `docs/plans/2026-09-22-backend-core.md` Tasks 1-18, and its section "Amendments after Task 10", which binds here too.

## Global Constraints

- Everything in the core plan's Global Constraints applies unchanged.
- Request and response types for `/api/*` are generated from `api/openapi.yaml` with oapi-codegen (types only, not a server framework). Hand-written wire types are prohibited; a contract change must break the build.
- Every error body is the contract's `Error` with a code from the contract. Handlers never put an internal error's text in `message`.
- Every mutating admin action writes an audit event, and the audit detail never contains a secret.
- Mutating `/api/*` requests must carry `Content-Type: application/json`, otherwise 415. With a `SameSite=Lax` cookie this closes cross-site form posts without a CSRF token.
- Account changes go through `gateway.AddAccount / SetAccountDisabled / RemoveAccount`, never the core auth manager directly.

## Task B1: Admin users and service accounts

**Files:** `internal/app/admin_users.go`, `internal/iface/http/admin_users.go`, tests beside each. No new migration: the one schema file, `internal/infra/postgres/migrations/0001_init.sql`, is amended in place while nothing has been released.

- [ ] `ListUsers`, `GetUser`, `CreateUser`, `UpdateUser`, `ResetPassword`, user tokens (list, issue on behalf, revoke) and `Activity`, each admin-only and each audited.
- [ ] `CreateUser` for a human with `signIn: password` issues a temporary password (72 h expiry — the constant `app.TemporaryPasswordTTL`, not a setting — and `must_change_password`), returned once. With `signIn: oidc` it records a pending identity for that address instead, written with **exactly** the configured issuer string (a trailing-slash difference makes the invitation silently unredeemable). The case-insensitive unique index on `pending_identities (issuer, lower(expected_email))` already exists (Task 16, D7): re-inviting an address first deletes or replaces its stale row, expired or not. A service account gets no password and no identity.
- [ ] `UpdateUser` refuses a policy change when `PolicySource == idp` **and the OIDC group mapping is configured** (`policy_managed_by_idp`). When no mapping is configured any more, an `idp` policy is frozen, not managed: the update converts it to `local` and applies the change, so removing the mapping never leaves users an admin cannot edit. Every rule goes through `access.ParseRule`; the first bad one is `invalid_rule` with `field` set to it.
- [ ] **Blocking a user deletes their sessions.** Sessions are already refused at read time for a blocked user, but the rows survive, so unblocking within the session window would resurrect old cookies. Deleting them makes a block a real revocation. Tokens need nothing: `CanUseAPI` already refuses them on the next request.
- [ ] An administrator cannot block themselves or remove their own admin role — the last-admin lockout.
- [ ] `GET /api/admin/catalog` and `POST /api/admin/policy/preview` read the gateway's model catalogue (amendment A6 as superseded: a synchronous read of upstream's registry, reached through the `app.ModelCatalog` port), applying exactly the gate's rule (`access.Policy.Covers`): a model is covered only if every provider serving it is allowed.

**Tests:** the one-time secrets; the IdP lock; invalid-rule reporting; blocking deletes sessions; the self-lockout guard; preview agreeing with the gate on a model served by two providers.

## Task B2: Vendor accounts with the login wizard

**Files:** `internal/app/providers.go`, `internal/infra/gateway/login.go`, `internal/iface/http/admin_providers.go`, tests.

- [ ] `GET /api/admin/providers` lists the gateway's accounts with status, last error, last refresh and the latest quota signals per window (kept by the usage sink from vendor response headers — expose them through a small read port rather than scraping metrics).
- [ ] **Login wizard (as built — upstream's embedder path in `sdk/api`).** `gateway.NewLogin` builds upstream's management handler with `NewHandlerWithoutConfigFilePath` and calls it directly; nothing is routed. `start` calls `RequestAnthropicToken` (Claude) or `RequestCodexToken` (ChatGPT) on a synthetic gin context without `is_webui` and reads `{url, state}` from the JSON it writes; without `is_webui` upstream binds no callback listener and leaves a goroutine polling the auth directory for the login's callback file. `complete` requires the pasted URL to carry a code and the session's `state` (otherwise `login_failed`, and the session stays pending for another paste), claims the session once, and hands the code over with `WriteOAuthCallbackFileForPendingSession`. Upstream exchanges it and passes the record to the post-auth hook (`SetPostAuthHook`), which gives it to the waiting `complete` and returns an error so upstream saves nothing itself. A pending login expires 5 minutes after `start` (upstream's waiter gives up then); `complete` waits at most a minute for the exchange; at most 8 logins are pending (`login_busy`, 409); an expired, finished or already claimed session is `login_expired`. Every ending calls `CompleteOAuthSession`, which stops upstream's goroutine.
- [ ] On success the credential goes through `gateway.AddAccount`. **Carried from Task 10's breaker ruling:** `AddAccount` currently reports success even when upstream's `Register` fails to persist, and for an account submitted already disabled the file store writes nothing — the account then vanishes on restart. Fix it here, the same way `SetAccountDisabled` was fixed: save through the gateway's store after `Register` and return that error. An account that is not saved, or whose `account_add` audit fails, is withdrawn again (`RemoveAccount`): no credential enters service unrecorded.
- [ ] `PATCH` disables/enables through `SetAccountDisabled`; `DELETE` goes through `RemoveAccount`. Audited.
- [ ] Provider names on the wire are policy-facing names (`claude`, `chatgpt`), mapped by the same single function amendment A6 defines.

**Tests:** start → complete against a stubbed upstream start handler; no listener bound; a callback for another sign-in refused; expiry and reuse refusal; the pending-login bound; `AddAccount` returning a persistence failure; an unaudited account withdrawn; disable and remove going through the gateway.

## Task B3: Settings and prices

**Files:** `internal/app/settings.go`, `internal/app/prices.go`, `internal/iface/http/admin_settings.go`, `internal/infra/metrics/prices.go`, tests. `model_prices` is a table in `0001_init.sql` (amended in place), not a new migration.

- [ ] The editable upstream configuration is stored in `settings` as YAML. `GET` returns it and the typed fields; `PUT` accepts either whole YAML or typed-field patches, parses into `sdk/config.Config`, and rejects fields the gateway owns with `forbidden_setting` naming the field: listen host and port, auth directory, `remote-management`, `api-keys`, and the credential families that are boot-only (`*-api-key`, `openai-compatibility`) — those require a restart and are refused at runtime rather than silently ignored.
- [ ] Every `PUT` returns a unified diff against the running configuration; unless `dryRun`, it applies through `gateway.PushConfig` and persists only after the push succeeds.
- [ ] `model_prices` table and `GET`/`PUT /api/admin/prices`. The metrics collector reads prices to produce the cost estimate (`llmproxy_cost_usd_total` and `llmproxy_cost_unpriced_tokens_total`), replacing any price source the core plan assumed; a price change applies to records from then on.

**Tests:** forbidden fields refused; dry run applies nothing; apply persists only on a successful push; cost computed from the stored price and unpriced tokens counted.

## Task B4: Composition root and three listeners

**Files:** `cmd/gateway/main.go` (calls `boot.Run` and nothing else), `internal/boot/boot.go` (the composition root — its own package, since it imports `internal/iface/http` and so cannot live in `app`), `internal/config/config.go`, `docker-compose.yml`, `.env.example`.

- [ ] Boot order: load config → migrate → pool → repositories → bootstrap admin (print the temporary password once, to stderr, never through the logger) → build the upstream boot configuration **from the database** (amendment A3) → gateway `New` with the token resolver, usage sink, gate observer, core auth manager and token store (the policy gate, its model-list filtering and the synchronous catalogue are built inside `New`) → `Run`.
- [ ] Three listeners: `LLMPROXY_LISTEN_ADDR` (proxied API, published), `LLMPROXY_WEB_ADDR` (the `/api` web API, reachable only from the frontend container), `LLMPROXY_METRICS_ADDR` (`/metrics`, reachable only inside the network). The proxied listener's policy gate stays default-deny.
- [ ] Graceful shutdown on SIGTERM: stop accepting, drain in-flight requests with a deadline, flush the usage sink, close the pool.
- [ ] Update `docker-compose.yml`: the frontend's `BACKEND_ORIGIN` points at the web listener; only the proxied listener is published; networks are segmented — the web listener only on a frontend↔backend network, postgres only on a backend↔database network, metrics on a network an operator's scraper joins.
- [ ] An end-to-end test boots the whole process as `main` does (against the wire-level fake vendor and a test Postgres) and proves: the bootstrap admin can sign in on the web listener; the proxied listener rejects the web API paths and the web listener rejects the proxied ones; `/metrics` is absent from both public-facing listeners.

**Acceptance:** `docker compose up --build` in this repository brings up postgres, backend and frontend healthy; the bootstrap temporary password appears once in the backend's log.
